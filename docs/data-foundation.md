# 数据底座方案

## 目标

数据层的目标不是一次性把所有数据都抓全，而是建立一套可以持续扩展的流水线：

```text
公开 API / 手工文件
        ↓
原始数据留存 raw
        ↓
标准化 clean
        ↓
指标计算 model
        ↓
前端发布 dataset
        ↓
站点模块使用
```

未来页面不应该直接依赖某个 API 的原始字段，而应依赖我们自己的标准化数据模型。这样以后换数据源、补手工数据、修正口径，都不会把前端页面打乱。

## 数据分层

### 1. raw：原始数据层

保存从 API 或手工文件拿到的原始数据，尽量不改字段、不改格式。

用途：

- 保留数据来源证据
- 方便复算
- 排查口径差异

建议路径：

```text
data/raw/api/
data/raw/manual/
```

### 2. clean：标准化层

把不同来源的数据统一成内部字段。

统一动作包括：

- 股票代码格式统一
- 日期格式统一
- 币种和单位统一
- 行业分类统一
- 缺失值和异常值标记

建议路径：

```text
data/clean/
```

### 3. model：指标模型层

在标准化数据上计算投研指标。

例如资本周期模块：

- capex / depreciation
- ROIC
- ROE
- 现金流 / 营业利润
- 资产负债率
- 三年趋势
- 行业分位数
- 阶段分类
- 研究池得分

建议路径：

```text
data/model/
```

### 4. public：前端发布层

把模型结果导出为前端可直接读取的轻量数据。

当前项目使用：

```text
data.js
```

中期可以改成：

```text
public/data/capital-cycle.json
public/data/liquidity.json
public/data/reports.json
```

## 数据源分级

### A 级：自动化优先

这些数据适合优先接 API，形成定期更新。

- 行情数据
- 估值指标
- 财务报表
- 财务指标
- 宏观利率、信用、通胀、货币数据
- 指数成分和行业分类

### B 级：半自动化

这些数据可以 API + 手工复核。

- 行业分类映射
- 公司主营业务标签
- 研究池人工备注
- 深度报告标签
- 特殊行业口径调整

### C 级：手工维护

这些数据通常不好自动抓，但对研究有价值。

- 研究结论
- 风险提示
- 行业专家纪要
- 报告摘要
- 自己的判断变化记录

## 建议数据源组合

### A 股与港股基础数据

优先顺序：

1. AKShare：覆盖面广，适合快速接公开数据。
2. Tushare Pro：质量较好，但需要 token、积分和频次管理。
3. BaoStock：适合 A 股行情和部分财务/宏观数据的补充。
4. 手工 Excel：用于暂时没有稳定 API 的字段。

### 宏观与流动性数据

优先顺序：

1. FRED：适合美国宏观、利率、信用、流动性相关时间序列。
2. AKShare 宏观接口：适合中国宏观、利率、货币、商品等公开数据。
3. 手工文件：用于央行、交易所、行业协会中不稳定或格式复杂的数据。

## 数据源选择原则

选择数据源时按下面顺序判断：

```text
是否公开合法
↓
是否可自动化
↓
是否稳定更新
↓
字段是否够用
↓
历史数据是否完整
↓
是否可交叉验证
```

如果一个数据非常重要但 API 不稳定，可以保留手工通道。手工数据不是失败，而是数据工程里的“人工校验入口”。

## 更新节奏

建议分三类任务：

### 日频

- 行情
- 估值
- 市场宽度
- 流动性价格指标

### 周频

- 行业状态汇总
- 研究池变化
- 流动性框架结论

### 月频或季频

- 财报指标
- 资本周期阶段
- 行业深度复核
- 方法论和口径修订

## API Key 管理

不要把 token 写进前端代码或提交到 GitHub。

建议使用本地环境变量：

```bash
export TUSHARE_TOKEN="..."
export FRED_API_KEY="..."
```

后续可以增加 `.env.example`，只写变量名，不写真实 token。

## 第一阶段落地

第一阶段不要急着自动化所有数据。建议先做四件事：

1. 建立数据目录结构。
2. 建立数据源登记表。
3. 把当前 `data.js` 视为发布层产物，而不是唯一数据源。
4. 为资本周期模块设计一条从原始数据到前端数据的可复算流程。
